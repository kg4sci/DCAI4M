## O · Output & Decision Role

**Score**: 2; scored
**Criterion**: Multi-property prediction, candidate ranking, or risk assessment. 
**Rationale**: Taking the frozen entire Matbench suite as the unit, formal evaluation covers multiple types of material property prediction. Each subtask still predicts only a single target; the multi-property here refers to the suite scope, not the same model jointly outputting multiple properties.
**Level comparison**: Score 1 accurately describes a single subtask; score 2 describes the selected suite's formal prediction scope across optical, mechanical, electronic, and other properties. The source has no candidate generation, inverse design, or next-step experiment decision, so scores 3 and 4 do not apply.
**Task**: T-suite
**Boundary & dispute notes**: "multi-property prediction" could also be strictly understood as multiple outputs of the same model; this judgment relies only on the suite formally including multiple property tasks, without describing it as a joint multi-output model.
## A · Adaptivity & Sequentiality

**Score**: 0; scored
**Criterion**: Completely static, one-shot prediction. 
**Rationale**: Each fixed task maps material input to target prediction, and five-fold evaluation repeatedly trains and tests models, but does not stipulate selecting the next candidate or updating discovery actions based on new material results. TPOT's iteration only selects prediction pipelines inside the reference model.
**Level comparison**: Score 0 corresponds to a single target prediction for fixed material input. The explicit conditional behavior update required by score 1 is not established by ordinary input mapping; score 2 active selection, score 3 offline multi-round materials optimization, and score 4 closed loop all differ from the described fixed-fold testing and internal TPOT optimization object.
**Task**: T-suite
**Boundary & dispute notes**: TPOT's use of genetic programming or five-fold cross-validation cannot make the model's internal iteration count as sequential feedback of the materials task.
## I · Workflow Integration

**Score**: 3; scored
**Criterion**: Multiple models or modules connected in sequence. 
**Rationale**: The Automatminer reference implementation formally evaluated by the paper chains material feature generation, cleaning and reduction, AutoML model selection, and prediction. This capability is limited to the evaluated reference pipeline; there is no evidence that Matbench requires all external evaluated models to adopt this structure, nor does it form a discovery system spanning experiment planning and feedback updating.
**Level comparison**: Relative to 1 and 2, Automatminer contains explicitly chained feature, preprocessing, and AutoML modules, fitting score 3's "Multiple models or modules connected in sequence"; but these stages serve a single prediction task, not connected to experiment planning or task-level feedback, so 4 is not taken.
**Task**: T-suite
**Boundary & dispute notes**: Another strict interpretation would treat the model's internal preprocessing as level 2 "An enhanced version of a single task"; 3 is taken here because the anchor explicitly allows "module" chaining, and the paper describes the actual execution order stage by stage. This boundary should accept independent review.
## G · Goal & Constraint Handling

**Score**: 1; scored
**Criterion**: A single optimization objective. 
**Rationale**: Each regression or classification subtask is evaluated separately by predictive performance; the evaluated reference algorithm uses internal validation to select and optimize the prediction pipeline. Data selection screening and Express computation time limits belong to construction and computational conditions respectively, and cannot serve as formal material candidate constraints.
**Level comparison**: There is a clear predictive model performance objective, so it is above 0. Each subtask's MAE or ROC-AUC and internal validation objective are used separately, not constituting multiple material objectives optimized simultaneously; data screening and computational budget also do not constitute static constraints on candidate decisions, so scores 2 to 4 have no basis.
**Task**: T-suite
**Boundary & dispute notes**: MAE and ROC-AUC appearing across tasks, or TPOT having a runtime limit, do not indicate the same materials decision simultaneously optimizes multiple objectives or resource constraints.

## P · Autonomy & Actionability

**Criterion**: Automatically executes a fixed workflow. 
**Rationale**: The evaluated Automatminer reference implementation completes material feature processing, model search, and property prediction per presets without researchers tuning each item; the paper emphasizes the same Express configuration is used for all Matbench tasks. The automatic execution scope is predictive modeling, not material experiment execution or feedback planning.
**Level comparison**: Compared with score 0 giving only predictions and score 1 humans deciding actions, the evaluated reference implementation automatically executes fixed modeling steps, fitting 2; the preset does not select the next action based on material feedback, and there is no planning, execution, and correction of the whole discovery process, so 3 or 4 is not taken.
**Task**: T-suite
**Boundary & dispute notes**: Automatic training and execution of the prediction model are sufficient to support the fixed-workflow level; this does not mean all external models of the benchmark have equivalent automation.
## E · Dependence on Experimental Results

**Score**: 2; scored
**Criterion**: Real experimental results serve as formal testing; performance can be independently evaluated on experimental data. 
**Rationale**: Table 1 lists experimental band gap and steel yield strength as formal tasks marked Experiment. Methods stipulates five-fold testing for each task; Fig. 3 shows test metrics separately for each task, so experimental-source tasks can be evaluated independently. Experimental results come from historical data, and the paper does not claim new physical experiments.
**Level comparison**: Level 0 requires no real experimental results, which does not fit the Experiment label in Table 1; level 1 has only training, calibration, or a few cases without formal experimental testing, which does not fit the five-fold testing and per-experiment task reporting; level 2's formal experimental testing and separate evaluation both have evidence.
**Task**: T-suite
**Boundary & dispute notes**: The suite also contains computational tasks; this judgment refers only to the experimentally labeled task formally evaluated within it, without counting Best Literature external results. E measures the basis for experimental testing and does not require all tasks to be experimentally sourced.
